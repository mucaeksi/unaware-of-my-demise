# Android real-device acceptance plan

Source audit: `5c83e3d1`, 2026-10-11. This is a **test plan**, not executed device evidence. English UI/subtitles; Japanese dialogue audio (`ja-JP`). First release is Android/Google Play; browser and emulator results alone cannot pass this gate. Source: README first-AAB acceptance, `docs/AAB_ACCESS_PLAN.md`, `apps/game/src/{platform/native,net/identity,net/store,net/api}.ts`, native plugins in `apps/android/android/`, and `apps/api/src/{player,account,billing,ads,progress}/*`.

## Test setup and evidence record

1. Use the Play internal-testing AAB for `io.github.mucaeksi.unawareofmydemise`, versionCode recorded, with staging API only. Check upload and Play app-signing SHA-1 on the Android OAuth client; Credential Manager returns the Web-client audience configured as `GOOGLE_CLIENT_IDS`. Use licensed test accounts and active Play sandbox products, not real charges.
2. Test on at least two physical devices: API 24/minSdk-compatible device and a current Android device; include low-memory/slow-network and cutout landscape device. Record model, Android/WebView versions, RAM, install source, commit/AAB hash, release generation, API environment and UTC timestamp (owner reports may show Istanbul time). Emulator is supplementary.
3. Use Google sample/test-device rewarded ads and UMP debug geography only on designated test builds. Native `UomdAds` must never use production traffic for repeated QA. Test-key AdMob callbacks intentionally return `test_callback` and grant **no tokens**: a real test ad is an SDK/UI test, not proof of end-to-end financial fulfillment. For cap/concurrency backend tests use a separately authorized isolated test harness; do not mint fake signed callbacks against live staging.
4. Establish two Google users A/B and independent app player IDs. Record IDs privately in test evidence, never tokens, ID JWTs, purchase tokens, signatures, keystore passwords or exported personal data in Git/screenshots. Access-protected Control Center and D1 read-only queries provide backend evidence.
5. Capture starting wallet, purchase orders/periods, ad window count, mail source keys, progress/save version and active flags. No direct SQL wallet adjustments: account setup uses authorized audited test-player grants only.
6. For every case record PASS/FAIL/BLOCKED, actual vs expected, request status/error code, redacted relevant table counts/IDs, screen recording and sanitized logcat/Worker logs. A missing bridge, Console product, native screen or backend transition is BLOCKED/FAIL, never waived as a mockup success.

## Google-only identity and account lifecycle

**AUTH-01 successful identity and stable subject.** Fresh install → Account → Sign in with Google → choose A → return to game → relaunch. Expect only Google sign-in, verified internal ID, server session, initial grants exactly once. GET me/wallet agree with D1. Logout and sign in again under changed Google display name/email: same verified `sub` maps to same player, no fresh grants. Evidence: one active `players` mapping, sessions created/revoked, no duplicate `signup` ledger entries. No guest or anonymous permanent progress account.

**AUTH-02 cancellation / no account / unavailable service.** Cancel Credential Manager, remove available Google accounts on a dedicated test device, and deny network. Expect understandable English error/cancel and no authenticated account or wallet grant; later retry works. Evidence: no new player/session on failed auth, `UomdGoogleSignIn` error codes, redacted HTTP logs.

**AUTH-03 invalid tokens.** In isolated API test harness submit expired token, wrong aud, wrong iss, forged signature, missing sub, unsupported algorithm, missing token and an oversized body. Expect rejected request, no player/session/grant; rate-limit abusive retries. Native happy-path must still work afterward. Evidence `player/auth.ts` validation/error status and unchanged tables. Do not log raw JWTs.

**AUTH-04 app session expiry, logout and revocation.** Use an isolated clock-controlled session or naturally expired session; reopen, then sign in. Log out and replay an earlier app session in the harness: rejected; other-device logout behavior matches implemented per-session revocation. Revoke Google app access from Google account settings and try fresh Credential Manager sign-in. **Acceptance requirement:** revoked identity must not leave permanent access; document maximum app-session lifetime and enforcement gap. Current Worker sessions do not continuously check Google account revocation; no dedicated refresh endpoint is shown. A live app session surviving upstream revoke must be logged as a blocker until policy/implementation is resolved, not called PASS. Evidence `sessions`, me responses and provider behavior.

**AUTH-05 account separation / reinstall / recovery.** Progress A, logout → B → confirm different player and no A data. Uninstall and install the same Play build → sign in A → server roster/wallet/progress restored. Repeat on another physical device with A. Local preference/patch caches can reset; authoritative cloud progression must persist. Reinstall must not reclaim signup/mail/task/battle/purchase grants.

**AUTH-06 export and deletion.** As A populate purchases/mail/progress/gear, export → verify all fields and `truncated` flags. Send wrong confirmation → rejected/unchanged; then UI-confirm exact `DELETE`. Expect current/all A sessions unusable, no mutable wallet/save/roster/team/task state, google_sub and display_name removed, deleted tombstone retained. Verify retained ledger/pulls/purchases/mail, ad records and audit trails match disclosure; they are not “all erased.” Re-sign-in A → NEW internal player with no old progress; an old purchase must not be granted to new identity (`account_mismatch`/order ownership). Subscription cancellation must be handled in Play; account deletion alone does not cancel Google billing. **UNKNOWN:** public web deletion request URL and retained-data schedule; blocks store compliance until set.

## Google Play purchases and subscriptions

**BILL-01 consumable.** Read product mapping and native Play-formatted price → purchase licensed test consumable → approve Play dialog → wait for server verification. Expected only confirmed `purchased` state grants once, obfuscatedAccountId matches GET me billingTag, product/package/state validated by Play Developer API. `purchases` unique order/token mapping and ledger delta equal configured grants; consume/ack path succeeds. Repeat same verification/restore concurrently: `already_granted`, no extra currency/items. Evidence native dialog + `purchase_events`, Play consumption state, D1 acknowledged marker, order row and ledger idempotency keys.

**BILL-02 cancellation / unavailable / API failure.** Cancel checkout, request inactive/unknown product, disconnect before verification, fail Play Developer API response in isolated harness. Expect no optimistic client credit. After reconnect native owned-purchase restore retries confirmed transactions exactly once; record errors if restore silently swallows them. Native purchase response is not proof of fulfillment.

**BILL-03 pending purchase.** Select Play slow test payment: pending → close/restart app → verify wallet unchanged → complete payment → restore. Expect `pending` grants nothing, successful later verify grants once; cancelled pending never grants. **Current source limit:** one-time RTDN only records `one_time`, and does not grant; `net/store.ts` requires a later restore/verify. Do not claim RTDN alone fulfills pending consumables. If app does not expose/automatically invoke restoration, record a release blocker. Check product event/order/ledger timestamps.

**BILL-04 token/product/account mismatch.** In the harness reuse A order on B, wrong product/package, cancelled purchase, refunded order and one token bound to multiple IDs. Expect rejection/no B grant. Purchases from deleted A must not transfer by email identity. Evidence Play lookup + accountTag comparison + unique order ownership.

**BILL-05 subscription initial, renewal and mailbox.** Buy test subscription with exact mapped base plan/offer → confirmed period → inspect period_start/end, instant grants and periodic mail. Reopen mailbox repeatedly in same 12 h window: one `sub:<order>:hd:<k>` mail, claim once; later window creates next offering, no future offerings. Accelerated Play renewal creates new Google order/period with one grant. RTDN types 1/2/4/7 reverify Play; duplicated messageId yields `duplicate`; duplicate orders do not grant twice. Verify configured duration/periodic count, not assumed 30-day timing in accelerated sandbox.

**BILL-06 cancellation, expiry, grace/hold and restart.** Cancel in Play → benefits remain only through legitimately entitled period. Let test period expire → no further benefits. Enter Play grace, hold, pause, recovery/restart paths → verify Developer API state and expected current entitlement, no premature grants. Current `verifyPurchase` accepts active/grace and unexpired cancelled state; `handleRtdn` merely logs non-granting state changes as `state_noted`. Check whether old D1 period still yields benefits after an early hold/pause/revoke. Required acceptance is correct effective entitlement in every state; if state transitions only log without enforcement, FAIL and send Claude the exact reproducible order/state. There is no separately evidenced subscription status reconciliation scheduler.

**BILL-07 refund/revoke before and after spending.** Refund consumable/renewal in Play test orders → send authenticated Google notification → expect refundable configured currency debited up to available balance, no negative wallet. Any unreturned amount is in `purchases.unrecovered`. Subscription mail and noncurrency goods need explicit clawback policy: do not assert complete removal if code only reclaims currency. Duplicate refund/revocation must not debit twice. Check state `refunded`, purchase_events, ledger refund entries, wallet reconciliation and whether existing unclaimed mail remains claimable. Current refund code does not retract already-created or claimed subscription mail; record that gap against the required entitlement policy. UNKNOWN: behavior for each noncurrency grant and mail cancellation; required before shipping such products.

**BILL-08 webhook auth/retry/out-of-order and acknowledgement.** Real Pub/Sub push test notification with correct OIDC → test event; wrong audience/service account/expired token/no token → rejected. Record `rtdn_seen` only after authorized push. Duplicate/out-of-order grant/refund notifications → authoritative Play state wins, no resurrection/double debit. Transient Play failure → message ID deleted to permit redelivery. Watch `ack_failed` and `consume_failed`; current duplicate consumable verify retries consume, but acknowledged-subscription retries and scheduled retries need proof. Kill app between Google purchase, backend grant and native return → restore without loss/duplication. No token values in trace artifacts.

## Rewarded ads and UMP

**ADS-01 test ad / consent happy path.** Fresh native launch in UMP debug EEA profile → required message → make consent choice → SDK canRequestAds state → voluntary Rewarded button. Verify AdMob displays test label, SSV userId/internal ID and nonce are assigned, close callback does not grant client currency. Test-key callback returns `{granted:false,reason:test_callback}`; wallet unchanged is correct. Full financial path uses isolated backend verification tests, and a separately authorized designated-device live SSV observation only if needed under AdMob rules.

**ADS-02 early close/no-fill/offline.** Close before reward, force no-fill/network error, deny ads consent → no reward/ledger, clear useful English feedback, no ad in battle target selection or emotional dialogue/cinematic. Rewarded is optional; no story lock requiring ads. Evidence SDK error state and unchanged `ad_rewards`/wallet.

**ADS-03 signed-callback fraud / replay / nonce.** Isolated harness: valid signed callback, duplicate transaction ID, wrong unit, wrong user nonce, used nonce, expired (>30 min) nonce, callback older than 24 h, bad signature/unknown key/tampered apostrophe encoding. Only a valid live-key configured-unit callback grants current AD.token=30 once. Verify `ad_nonces.used_at`, unique `ad_rewards.transaction_id`, ledger `ad:<transactionId>`; timestamp/nonce checks and atomic batch protect duplicates. Current grant uses server payout, not untrusted reward_amount.

**ADS-04 5 per rolling 12 h boundary.** On isolated test time schedule accepted callbacks at t0,t1,t2,t3,t4, all within 12 h → exactly five rows and +150 tokens under current placeholder payout. Sixth: begin HTTP 429 `ad_cap_reached`, callback no grant `window_cap`. At t0+12 h exactly, server query uses `at > now−12h`: oldest reward leaves window, nextSlotAt/free slot correct. Crossing midnight alone does not reset. Two devices/concurrent callbacks must share one player cap; simultaneously submit two when count=4 → only one grant. Do not watch live ads repeatedly or change the physical device clock to fake server time.

**ADS-05 nonce issuance guard.** Request begins with no completed views: nonce expires in 30 min. Twenty issued requests in previous 24 h consume issuance allowance even if unused (query counts all recently created nonces); 21st returns `too_many_requests`. Check per-minute begin limit as well. Source comment says “open” but SQL counts used and unused: record actual behavior, no promised renewal on closing ad.

**CONSENT-01 grant/refusal/withdrawal and privacy options.** Test EEA/UK/Swiss UMP profiles as test geography only, then nonregulated profile. Cancel required form, network failure on initialization, consent refusal, consent granted and post-launch withdrawal through Privacy options. Ads never request when canRequestAds=false; privacyOptionsRequired=true exposes the actual form. Relaunch retains/refetches UMP choice correctly. No app-owned consent record exists in D1; evidence SDK state/device storage and observable requests. Verify under-age/child-directed flags against approved age policy; UNKNOWN policy/age screen must be resolved before release. Do not equate “refused personalized ads” with “no permitted ads” if UMP still allows a request; SDK state governs, accurate user disclosure remains required.

## Offline, resume, patching and first-content completion

**LIFE-01 network loss and interrupted server result.** During sign-in/purchase/ad/save/battle verification toggle airplane mode and switch Wi-Fi/mobile. Gameplay can use valid cached content, but no unverified economy/progress grant. Reconnect/retry same idempotency request without duplicate debit/grant. Old save version returns conflict (no last-writer silent loss). Native back/background/force-stop at each boundary → truthful “pending/not verified” state, not success.

**LIFE-02 audio/video/WebGL.** During opening/dialogue/battle background 30 s, lock/unlock, incoming audio interruption, return after OS process kill. Expect restore safe checkpoint, audio lifecycle without doubled tracks/voices, Japanese voice synced to English subtitle IDs, no skipped choice or unintended purchase/ad. Physical-device context-loss and decoder support; record cold start, memory, frame pacing and long-session crashes, not browser FPS claims.

**PATCH-01 unchanged AAB data patch.** Record original versionCode/hash → install approved staging signed scene+new character/chibi+boss/banner+cinematic/BGM patch → reload → verify all new content works and server replay agrees, versionCode unchanged. Wrong signature/hash, path traversal, incompatible schema/client range, interrupted/resumed transfer, low storage, dependencies missing → reject safely, preserve last working version. Rollback/kill uses newer manifest generation; older replayed generation rejected. New unsupported ops must fail activation, never download executable code.

**CONTENT-01 opening → three tutorials → Finish.** On real device play complete approved ~120 s anime opening, tutorial sections T-1/T-2/T-3 with in-between cinematics, choices/skip/replay, then Finish save. Check each section checkpoint and server-verified battle, English only, Japanese VO, free/guest party access without pulls, landscape safe areas/touch text readability. Existing embedded T-1 and prototype T-2 are not proof of complete first-AAB content. Mark missing opening/T-3/media as BLOCKED.
